# Контракт разработки и релизов GROME

## Единственный путь к production

GitHub `master` — каноническая версия исходного кода. Рабочие сессии Codex Desktop и Codex CLI открывают один и тот же локальный клон либо отдельные worktree от него; они не являются источниками релиза сами по себе.

Путь изменения всегда такой: локальная ветка → проверка → commit → GitHub `master` → GitHub Actions → VPS. Запрещены прямые правки, `scp`, копирование папок и `git reset` исходного кода в `/root/grom-dashboard` на VPS. Исключение — только код GitHub Actions, который разворачивает проверенный commit.

## До и после задачи

- Перед изменением: получить актуальный `master`, убедиться, что нет чужих незакоммиченных правок, и прочитать `PROJECT_CONTEXT.md`.
- Менять только файлы, относящиеся к задаче. Общие файлы (`server.js`, `index.html`, `adapter.js`, маршрутизация, стили) дополнительно проверять на влияние на остальные кабинеты и метрики.
- После изменения: выполнить релевантные регрессионные проверки, обновить `PROJECT_CONTEXT.md`, закоммитить ровно файлы задачи и отправить в Git.
- Если две сессии работают одновременно, каждая использует отдельную ветку/worktree. Слияние допускается только после прохождения проверок и отсутствия конфликтов.

## Граница кода и данных

Код, тесты, UI, документация и workflow хранятся в Git. Операционные данные и секреты живут только на VPS: расписание, ОВН-отчёты, роли, результаты синхронизаций, зарплатные расчёты, токены и журнал задач. Их нельзя добавлять в commit, удалять или перезаписывать релизом.

`adapter.js` на production — актуальный реестр мастеров, управляемый адаптером. Релиз не имеет права заменять его версией из рабочей копии.

## Инвариант релиза

После успешного релиза `/root/grom-dashboard/.release-version` равен SHA commit из GitHub Actions, а `.release-manifest` описывает развернутые кодовые файлы. Следующий релиз сначала сверяет manifest: любое ручное изменение production-кода останавливает релиз вместо молчаливого перезаписывания.
